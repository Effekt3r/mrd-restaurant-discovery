#### C-1 (Critical). A deep link that arrives after process death is dropped

**Where:** `app/src/main/kotlin/com/effekt3r/mrd/MainActivity.kt:28-32`

```kotlin
DisposableEffect(navController) {
    val listener = Consumer<Intent> { navController.handleDeepLink(it) }
    addOnNewIntentListener(listener)
    onDispose { removeOnNewIntentListener(listener) }
}
```

**How it fails:**
- The listener is registered by a `DisposableEffect`, which runs only after the first composition. Compose composes once the window is attached, and that happens after `onResume`.
- When the task survives but the process has died, Android recreates `MainActivity` with its saved state and delivers the link to `onNewIntent` before `onResume`. No listener is registered yet, so the link is lost.
- `NavHost` restores the saved back stack (Browse). It reads `activity.intent` only when the back stack is empty, and `getIntent()` is the intent that first created the activity anyway, not the new link.
- The design notes call a link to the running app a "warm start" and the `force-stop` case a "cold start", so this third state was never tested.
- On the device it fails 3 out of 3 times (§11). This is the normal way a link from a notification or another app reaches a backgrounded app on a real phone, because Android kills background processes routinely.

**Smallest fix:** register the listener in `onCreate`, before any intent can arrive, and hand the intent to the `NavController` once it exists:

```kotlin
private var pendingLink by mutableStateOf<Intent?>(null)

override fun onCreate(savedInstanceState: Bundle?) {
    enableEdgeToEdge()
    super.onCreate(savedInstanceState)
    addOnNewIntentListener { pendingLink = it }
    setContent {
        val navController = rememberNavController()
        LaunchedEffect(navController, pendingLink) {
            pendingLink?.let { navController.handleDeepLink(it); pendingLink = null }
        }
        // MrdTheme { … } as now
    }
}
```

**Test:** add a Robolectric test to `DeepLinkTest` that recreates the activity from saved state and delivers the intent before the first composition. Then repeat §11's `am kill` check.

- **How it fails:**
  - `ScrollToTopOnNewFilters` calls `requestScrollToItem(0)` when the state's filters change, and the request only covers the next measure pass.

## Observations outside the milestone's scope

- **Menu errors blame the connection while online.** A menu that failed for bad data (r-1086), and presumably a 5xx, reads "Check your connection and try again" while the device is online. Spec §5.4 words errors by connectivity alone, so this is as specified, but bad data isn't the user's connection. It might deserve its own wording, as `Storage` has.
- **Pull-to-refresh (AC-9)** shows its indicator over the list without blanking it (§10). I didn't check overlapping refreshes on the device, since that wasn't in this pass. The repository test from milestone 3 covers them.
- **TalkBack itself wasn't run.** The evidence is `uiautomator` and the Compose tests, as this check asked. Spec §6.5 still requires a full TalkBack walk as part of the release gate.
- **The 10,000-restaurant dataset wasn't run.** It applies only to debug builds. It's where M-1's race would most likely show.
- **Throttling didn't work.** `adb emu network speed gsm` and `delay gprs` had no visible effect on this emulator, so I caught the skeletons with `screenrecord`.
- **The Open now count lags a sync by up to a minute.** I found this in the re-run, in milestone 3's data layer.
  - `count()` (`core/data/src/main/kotlin/com/effekt3r/mrd/core/data/OfflineFirstRestaurantRepository.kt:68-73`) passes the minute tick as the query's `:now`, and Room re-runs the same query when `sync_state` changes.
  - The SQL counts a snapshot as fresh only while `:now - last_synced_at` is `BETWEEN 0 AND 1799999` (`RestaurantDao.kt:24`). After a sync that lands later than the tick, `:now` is earlier than the sync, so restaurants without hours count as Unknown until the next tick.
  - **On the device,** with Open now on:
    - A pull-to-refresh at 17:37:06 left "168 open now" for six readings to 17:37:28, and the 17:38 tick brought "176 open now". The model gives 176 with a fresh snapshot and 168 with a stale one.
    - After process death at 17:33, "10 open now" showed while the list's first card was Cape Point Flame Chicken, a restaurant without hours, read as "Open." The 17:34 tick brought 12.
  - The list stays right, because its PagingSource takes `clock.instant()` when Room rebuilds it.
  - `restaurant()` (`:75-78`) pairs the same tick with the sync time, so Details may read a restaurant without hours as Unknown for up to a minute after a sync. That's from the code; I didn't see it on the device.
  - **Fix:** take `now` as `clock.instant()` whenever the snapshot's time changes, e.g. `combine(ticker.ticks(), dao.lastSyncedAt()) { _, _ -> clock.instant() }` as the source of `now` in both.
